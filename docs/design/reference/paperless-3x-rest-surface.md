# The Paperless-NGX 3.x REST surface this server does not expose

This client was designed against the Paperless 2.x API and wraps thirty route
shapes. Paperless 3.1.3 publishes ninety-three. This page records what the
difference contains — most importantly the Paperless AI surface introduced in
3.0.0, which is reachable over REST but documented nowhere in Paperless's own
`api.md`. It records what exists and how it behaves; which of it is worth
exposing is a project decision kept in the tracker, not here.

## Scope

- Covers: the route inventory of 3.1.3 against the routes this client calls;
  the chat and AI-suggestion endpoints and how they are gated, framed and
  configured; and the shape of the read-only endpoints this client could
  adopt.
- Does not cover: payload version 9 versus 10, which is
  `paperless-api-versioning.md`; the version endpoints, which are
  `paperless-version-endpoints.md`; write semantics of routes this client has
  no reason to call; and any verdict on what to expose.
- Depended on by: the feature issues opened from #113. No module depends on
  this page yet, which is the point of it.

## Claims

### The size of the gap

- The instance publishes **93 distinct paths** in its OpenAPI schema; this
  client calls **30** of them, leaving 63 unwrapped.
  [source: live-schema]
  [observed: the schema fetched from the connected 3.1.3 instance and its path set compared against the `"/api/` literals in `src/paperless_mcp/client/*.py`, on 2026-09-17]
- The schema is the only complete description of the surface. `docs/api.md`
  documents neither chat nor AI suggestions: a grep for `chat`, `ai_sugg`,
  `llm` or `remote_ocr` across it returns only the bulk-edit `remote_ocr`
  parameter. [source: pngx-api-md]
- The schema is served at `/api/schema/` and is rendered for the default
  payload version only; a `?version=9` query parameter does not re-render it.
  [observed: `/api/schema/?version=9` and `?version=10` returned byte-identical documents, both declaring `info.version` `"6.0.0 (10)"`, on 2026-09-17]
- That schema is **vendored beside this page** as
  `paperless-openapi-3.1.3.json.gz` (33 KB compressed, 93 paths), with a
  plain-text `paperless-openapi-3.1.3.routes.txt` listing each path and its
  methods. The next refresh of this page diffs the route list rather than
  re-deriving it, and the compressed form stays under the repository's
  500 KB added-file limit. The capture is generated by Paperless from its own
  code: it declares no `servers` block and contains no archive content,
  hostname or credential. [source: live-schema]
  [observed: the vendored file gunzipped and re-parsed to 93 paths declaring `info.version` `"6.0.0 (10)"`, and grepped for hostnames, tokens and archive strings with no hits, on 2026-09-17]

### Chat

- The chat route is **`/api/documents/chat/`**, not `/api/chat/`. It is
  mounted by nesting `^chat/` under `^documents/` inside `^api/`.
  [source: pngx-urls]
  [observed: `/api/chat/` redirected to the login page, while `/api/documents/chat/` served the request, on 2026-09-17]
- It accepts **POST only**, and is reachable with **token authentication** —
  no session or CSRF cookie is required.
  [source: pngx-doc-views]
  [observed: `POST /api/documents/chat/` with an `Authorization: Token …` header returned HTTP 200 on 2026-09-17; the same path under `GET` redirected to `/accounts/login/`]
- The JSON body takes `q` (required, at most 4000 characters) and an optional
  `document_id`. With `document_id` the answer is scoped to that document;
  without it, the scope is every document the calling user may view, which
  makes the endpoint a retrieval-augmented query over the whole archive.
  [source: pngx-doc-views]
  [observed: the same question asked with and without `document_id` answered about that document and about an unrelated archive document respectively, on 2026-09-17]
- Permissions are `IsAuthenticated` plus `ViewDocumentsPermissions`, which
  maps POST to `documents.view_document`; an unreadable `document_id` is
  rejected per-document with 403, and an unknown one with **400, not 404**.
  [source: pngx-doc-views]
- When AI is disabled the endpoint returns **400 with the plain-text body**
  `AI is required for this feature`, before serializer validation.
  [source: pngx-doc-views]
- **The response is declared `text/event-stream` but is not SSE.** The
  generator yields raw model text with no `data:`, `event:` or `id:` framing,
  chunked. A standards-compliant SSE parser misreads it.
  [source: pngx-chat]
  [observed: a chat response whose first bytes were `OK\n\n__PAPERLESS_CHAT_METADATA__{...}` and contained no `data:` prefix, on 2026-09-17]
- Source references are appended as a **sentinel-delimited JSON trailer**, not
  as a separate event: the constant `"\n\n__PAPERLESS_CHAT_METADATA__"`
  followed by compact JSON `{"references":[{"id":…,"title":…}]}`, capped at
  three references. A client must split the stream on that delimiter to
  separate answer from citations. This is emitted by the server, so it is a
  contract rather than a frontend convention. [source: pngx-chat]
  [observed: the trailer `__PAPERLESS_CHAT_METADATA__{"references":[{"id":1,"title":"D&D 5e Basic Rules v1.0 [Full Color Edition]"}]}` on 2026-09-17]
- **Errors during streaming arrive as HTTP 200 with prose**, because the
  headers are already sent by the time they occur; a fixed error message, or a
  fixed "no content" message when the document set or the retrieval is empty.
  A caller cannot distinguish failure by status code. [source: pngx-chat]
- The view carries no `extend_schema`, so its request and response bodies are
  effectively undescribed in the OpenAPI document even though the path
  appears. [source: pngx-doc-views] [source: live-schema]

### AI suggestions

- AI suggestions are a **separate route**, `/api/documents/{id}/ai_suggestions/`,
  and the classic `/api/documents/{id}/suggestions/` is untouched by AI. The
  classic handler references no AI configuration at all; its response shape is
  fixed whether or not AI is enabled. [source: pngx-doc-views]
  [observed: on an instance with `ai_enabled: true`, `/suggestions/` returned only the classic `correspondents`/`tags`/`document_types`/`storage_paths`/`dates` keys while `/ai_suggestions/` returned five more, on 2026-09-17]
- This settles the question #113 raised: the endpoint this client already
  calls does **not** start returning AI-backed suggestions when the instance
  enables AI. [source: pngx-doc-views]
  [observed: as above, against an AI-enabled 3.1.3 instance on 2026-09-17]
- The AI response adds a `title` string and four `suggested_*` arrays of
  **names** (`suggested_tags`, `suggested_correspondents`,
  `suggested_document_types`, `suggested_storage_paths`) beside the classic
  arrays of **ids**. The id arrays hold entities that already exist; the
  `suggested_*` arrays hold proposed new ones that do not.
  [source: pngx-doc-views]
  [observed: a response carrying `document_types: [2]` alongside `suggested_document_types: ["Ruleset","Roleplaying Game Manual"]`, on 2026-09-17]
- Gating differs from chat only in its failure modes: 400 plain text when AI
  is disabled, 400 JSON `{"ai": ["Invalid AI configuration."]}` on a
  configuration error, and **503** `{"ai": ["AI backend request timed out."]}`
  on backend timeout. [source: pngx-doc-views]
- Suggestions are cached per backend, model, endpoint, language **and user**,
  and the cache stores only the model's raw choices, never resolved ids, so
  permission filtering re-runs for each requester.
  [source: pngx-doc-views] [source: pngx-ai-classifier]
- Whether the `dates` strings are validated to `YYYY-MM-DD` before being
  returned is not settled: they are passed through untouched, and only the
  workflow consumer parses them, skipping what it cannot read. [unverified]
  Reading the serializer that renders them, or observing a malformed date,
  would settle it. [source: pngx-ai-classifier]

### How AI is configured, and what that exposes

- Every AI and remote-OCR setting is exposed over **`/api/config/`**, whose
  serializer declares `fields = "__all__"`: `ai_enabled`, the LLM backend,
  model, endpoint, embedding backend and model, chunk and context sizes,
  output language and request timeout. [source: pngx-config]
  [observed: `GET /api/config/` returning `ai_enabled: true`, `llm_backend: "openai-like"` and an embedding backend, on 2026-09-17]
- The two key fields are obfuscated on read, rendered as a run of asterisks
  rather than omitted, and an all-asterisk value is dropped on write so a
  read-modify-write cycle does not overwrite the stored key.
  [source: pngx-config]
  [observed: `llm_api_key` returned as asterisks on 2026-09-17]
- **A database setting cannot disable what the environment enabled.** Each
  field resolves as `app_config.X or settings.X`, so with
  `PAPERLESS_AI_ENABLED=true` a stored `ai_enabled=False` is discarded by the
  `or`. [source: pngx-config]
- PATCHing any embedding-related config field queues a **full index rebuild**,
  making `/api/config/` a write surface with a heavy side effect.
  [source: pngx-doc-views]
- AI state also surfaces on two endpoints this client already calls or knows:
  `/api/ui_settings/` carries `ai_enabled` and a `remote_ocr` block, and
  `/api/status/` reports the LLM index status. [source: pngx-doc-views]

### Remote OCR and the "apply AI suggestions" action

- Remote OCR has **no endpoint of its own**. It is reachable as the
  `{"remote_ocr": true}` parameter of `POST /api/documents/reprocess/` (and of
  the legacy `bulk_edit` `reprocess` method), as workflow action type 7, and
  read-only through `ui_settings`. [source: pngx-api-md] [source: pngx-models]
- The 3.1.0 "apply AI suggestions" workflow action is reachable over REST for
  **configuration only**, as action type 8 on `/api/workflow_actions/` and
  nested under `/api/workflows/`, with `ai_suggestion_fields`,
  `ai_create_missing` and `ai_overwrite_existing`. [source: pngx-models]
- It cannot be invoked directly: execution is queued from a matching
  non-consumption workflow trigger, and `apply_ai_suggestions` is absent from
  the allow-list of `POST /api/tasks/run/`, so there is no "apply AI
  suggestions to this document now" call. [source: pngx-doc-views]
- The vector store likewise exposes no REST view; the one REST trigger that
  touches it is `POST /api/tasks/run/` with the `llm_index` task type, which
  is **superuser-only** and returns a task id even when AI is disabled, in
  which case the task no-ops. [source: pngx-doc-views]

### The rest of the unwrapped surface

Shapes below were read from the connected instance; each returned HTTP 200
with token authentication.
[observed: each path fetched with `Accept: application/json; version=10` against 3.1.3 on 2026-09-17]

- **Search.** `/api/search/` is a global search returning a single object
  keyed by object type (`documents`, `correspondents`, `tags`, `users`,
  `workflows`, `mail_accounts` and more) plus a `total`; it is not the
  document full-text search this client already reaches through
  `/api/documents/?query=`. `/api/search/autocomplete/?term=` returns a bare
  array of completion strings. [source: pngx-urls]
- **Document operations split out of bulk edit in 3.0.0**, each now its own
  POST route: `merge/`, `merge_as_versions/`, `rotate/`, `edit_pdf/`,
  `remove_password/`, `delete/`, `reprocess/`, plus `bulk_download/`,
  `selection_data/` and `email/`. The old bulk-edit methods still work at both
  payload versions. [source: pngx-urls] [source: pngx-api-md]
- **Document versions**, new in 3.0.0: a `?version={id}` parameter on the
  document detail, `download/`, `preview/`, `thumb/` and `metadata/`, plus
  `POST …/update_version/`, `PATCH|DELETE …/versions/{version_id}/`, and
  `GET …/root/` returning `{"root_id": …}`. [source: pngx-api-md]
  [observed: `/api/documents/1/root/` returning `{"root_id": …}` on 2026-09-17]
- **The task family beyond the list**: `GET /api/tasks/{id}/`,
  `/api/tasks/summary/` (per-type aggregates with counts and durations),
  `/api/tasks/status_counts/` (`all`, `completed`, `in_progress`,
  `needs_attention`), `/api/tasks/active/`, `POST /api/tasks/acknowledge/`
  and the superuser-only `POST /api/tasks/run/`. [source: pngx-doc-views]
- **`/api/trash/`** returns a paginated envelope of deleted documents carrying
  the full document shape including `deleted_at`, so a restore surface would
  reuse the existing document model. [source: pngx-urls]
- **`GET /api/documents/next_asn/`** returns a bare integer, the next free
  archive serial number. [source: pngx-doc-views]
- **`/api/documents/{id}/share_links/`** returns the share links of one
  document as a bare array, which this client currently approximates by
  filtering the global share-link list. [source: pngx-doc-views]
- **Share-link bundles**, new in 3.0.0, at `/api/share_link_bundles/` with a
  `rebuild/` action. [source: pngx-urls]
- **Administrative collections** this client does not touch:
  `/api/users/`, `/api/groups/`, `/api/profile/` (which exposes the calling
  user's own API token), `/api/mail_accounts/`, `/api/mail_rules/`,
  `/api/processed_mail/`, `/api/workflows/`, `/api/workflow_triggers/`,
  `/api/workflow_actions/`, `/api/logs/` (a bare array naming the readable
  logs) and `/api/config/`. [source: pngx-urls]

## Where this project departs from the subject

Nothing here is implemented, so there is no divergence to record. Two naming
traps are worth carrying forward, because both cost time in this pass:

- The chat route is under `documents/`, so `/api/chat/` — the path the route
  name `chat_streaming_view` and the URL fragment `^chat/` both suggest —
  redirects to a login page rather than 404ing, which reads like an
  authentication failure instead of a wrong path.
- `versioning.py` in `src/documents/` is about *document* versions, not API
  payload versions. See `paperless-api-versioning.md`.

## Not covered

  executed against the instance, deliberately, since it holds a real archive.
  [unverified]
- Whether `/api/config/` is readable by a non-privileged authenticated user.
  Stock DRF `DjangoModelPermissions` assigns `GET` an empty permission list,
  which would make the obfuscated config readable by any authenticated token,
  but Paperless's own tests exercise only a superuser. [unverified] Reading it
  with a restricted token would settle it.
- The `/api/search/` payload beyond its top-level keys, and whether it honours
  the same filters as the document list. [unverified]
- Any endpoint's behaviour on an instance without AI enabled; the connected
  instance has `ai_enabled: true`, so the disabled-path claims above are from
  source only. [unverified]
